# Per-test Cycle Count Criteria

Booley will model a Cycle Count Criterion as a specialized Simulation Criterion bound to one Target and named test, rather than folding performance thresholds into `sim_pass`. Absolute goals use inclusive `cycle_count_max` / `cycle_count_min`; baseline-relative bounds rerun the same Target and test at the Ticket's immutable `base_sha`, with synthesis-compatible implicit percentages and explicit `_cycles` variants for absolute deltas. The test must pass and produce unambiguous cycle evidence on every required revision; missing evidence fails closed.

Baseline and current workloads may differ while Target/test identity and execution controls remain sealed. Booley will still grade the observed Cycle Count numerically, but the review package must disclose every difference it can prove among declared, committed workload inputs and state that changed workloads prevent attributing the result solely to RTL performance. We chose disclosure over rejecting workload drift so Tickets can measure intentional testbench, vector, and firmware evolution, accepting that reviewers—not the numeric Criterion alone—judge whether such comparisons remain persuasive.
