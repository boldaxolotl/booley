Can one hybrid repository format stay readable and executable?

This demo tests a proposed data shape for Booley's public QA suite: stable structured records for machines, normative Markdown for people and agents, and an append-only execution stream for evidence. Click the files, drive the run, and look for places where the format becomes ambiguous or repetitive.

Prototype only. Nothing here is normative, complete, or intended for main. The PicoRV32 slice is deliberately tiny; it exists to make format decisions tangible.
Norms in MarkdownThe Scenario Protocol and Authoring Guide remain pleasant to review, with stable rule IDs that scenarios reference.
Design in YAMLScenario and coverage records use schema-validated YAML, keeping identifiers, graphs, gates, and allocations mechanically checkable.
Evidence in JSONLThe runner appends typed immutable events; summaries and Consolidate Findings handoffs are derived, never competing sources of truth.

Human review frontier

      
Decisions this prototype is asking you to make

      

        
1 · File boundary
Should the protocol and guide be Markdown while scenario and manifest facts are YAML, with JSON Schema beside them?
Recommendation: yes—do not encode long-lived norms as YAML prose.

        
2 · Scenario structure
Should assertions live beside the step that supplies their stimulus, while coverage allocations reference the stable scenario, step, and assertion IDs?
Recommendation: yes—optimize the primary review path, then index mechanically.

        
3 · Shared rules
Should scenarios bind a protocol major version and cite stable rule IDs instead of copying authority, evidence, retry, and cleanup prose?
Recommendation: yes—path + version + rule IDs; commit digest belongs in the Run Declaration.

        
4 · Runtime records
Should deviations, observations, Findings, checkpoints, and cleanup be typed JSONL events with derived human summaries and handoffs?
Recommendation: yes—one append-only truth, multiple disposable views.

        
5 · Identifier scope
Should IDs be globally stable dot-separated strings, even when nested in a scenario file?
Recommendation: yes for scenario/obligation/assertion; step and checkpoint IDs may be scenario-scoped.

        
6 · Runner seam
Should a future runner only validate, resolve, schedule, checkpoint, and emit records—never supply missing scenario semantics?
Recommendation: yes—missing semantics are schema/authoring failures, not runner defaults.
