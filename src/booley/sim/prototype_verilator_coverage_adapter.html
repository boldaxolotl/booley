Verilator coverage adapter decision lab

Validated answer: One deep adapter operation gives the Simulation Flow the required leverage while keeping Verilator coverage mechanics local—across instrumentation, generated/Cocotb/custom mains, Coverage Windows, unique raw files, parsing, native-merge verification, freshness, and collector-specific failures.

This demo captures the confirmed interface; it does not implement coverage. The walkthroughs show its invariants and deliberate failure modes.

Confirmed interface

What the Simulation Flow calls

collection = adapter.collect(
    request: CoverageCollectionRequest,
    execution: SimulationExecutionPort,
) -> CoverageCollectionResult
  • request: resolved Target, selected tests, report-artifact root, and trace dimension. The Target owns its Coverage Window; Coverage Criterion policy is deliberately absent.
  • execution: the existing generic build/run capability; the adapter chooses the variant and run envelopes.
  • result: simulation verdicts, collection status, native capability facts, collector errors, and durable artifact pointers.

What remains private

  • Explicit Verilator instrumentation flags and per-instance enablement
  • Generated-main, per-process Cocotb, and custom-main write/Window hooks
  • Unique raw database names, freshness stamps, and queryability checks
  • Version/header-gated native parsing and unknown record capabilities
  • Native merge invocation and independent merge-equivalence verification
  • Collector-specific error taxonomy and remediation text
